# 平台与存储

- **模块定位**：提供 EdgeDisk 的服务端运行环境、文件存储和异步任务基础。
- **对应代码**：`src/server/`、`src/db/`、`migrations/`、`wrangler.jsonc`
- **所属 M 里程碑**：[M0](../roadmap.md#m0)、[M2](../roadmap.md#m2)
- **当前状态**：M0 已完成，M2 进行中
- **最近更新时间**：2026-07-26

## 职责与边界

该模块负责 Access 身份校验、R2 文件读写、KV 分享记录、D1 任务与回收站记录、Queue 异步 URL 导入。浏览器页面布局和交互由 M1 前端模块负责。

## 结构与数据流

后台页面通过 `/api/*` 调用 Hono API。API 校验请求后交给 service 或存储函数，最终访问 R2、KV、D1 与 Queue。公开分享页通过 `/share-api/:code` 读取分享内容，通过 `/s/:code/file` 读取文件流。

## 关键决策

- 文件内容保存在 R2，目录通过前缀和空目录标记表达。
- 分享短链保存在 KV，并维护目标到分享码的反向索引。
- URL 导入采用 Queue 异步处理，D1 保存可查询的任务状态。
- 删除操作先进入回收站，彻底删除由单独接口完成。
- 目录列表采用游标分页，服务端只负责返回一页并透出游标，翻页由调用方决定翻到哪为止。服务端不做「一次性拉完整个目录」，避免超大目录把单次请求撑爆。

## 当前实现

现有接口覆盖目录浏览、上传、创建文件夹、移动或重命名、详情、分享、回收站和 URL 导入。M1 重设计沿用这些接口，不修改存储模型。

### 目录分页（M2）

R2 的 `list` 单次最多返回 1000 条。此前 `listDirectory` 和公开分享的 `getShareView` 都只调一次 `list`，也从不检查 `truncated`，超过 1000 条的目录会静默丢掉剩余内容——文件还在 R2 里，但界面上不存在、点不到，与「文件丢了」无法区分。

现在两处都改为游标分页：

- `listDirectory(env, prefix, { cursor, limit })` 返回 `{ prefix, folders, files, cursor, truncated }`，`cursor` 在列完时为 `null`。
- `GET /api/list` 接受 `cursor` 与 `limit` 查询参数。
- `GET /share-api/:code` 接受 `cursor` 查询参数，返回结构同样带上 `cursor` 与 `truncated`。
- `resolveListPageSize` 统一决定页大小：调用方传入优先，其次 `MAX_LIST_KEYS`，最后压到平台上限 1000。

`countDirectoryObjects` 和 `collectObjectKeys` 本来就有完整的游标循环，这次不动。

## 验证方式

- `npm run check` 验证严格 TypeScript。
- `npm run build` 验证 Worker 产物。
- `src/server/objects.test.ts` 用伪造的 R2 bucket 覆盖目录分页：游标透传、页大小裁剪、占位标记与回收站前缀过滤。

## 待扩展项

- 全盘搜索索引（M3）。
- 分享访问密码、下载日志和限速。
- 导入任务取消与失败重试（M3）。
- `moveObject` 的文件夹分支仍是逐个对象串行 `get` + `put`，大文件夹移动会顶到子请求上限，且中途失败没有回滚。
- 回收站没有保留期与自动清理。
- 文件响应统一是 `private, no-store`，公开分享无法走边缘缓存。
